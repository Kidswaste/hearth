# Round 159 · css159: dead CSS out, eager CSS lighter

The owner wants Hearth lighter. After 150+ rounds the first screen parsed 23 stylesheets (398 KB) and there was talk of
a lot of CSS left from removed or restyled UI (the Quests / Life tab, the music studio, VST plugins, the old Lab looks).
This round measured which rules can still match, deleted the ones that can't, and moved eager rules that only style
lazy UI into that UI's lazy group. Zero visual change was the rule.

Budget (`dev/boot-test.js`): sheets 24 → **20**, CSS 410 → **385 KB** (374 + 3 %).

Measured with `node dev/coldstart-report.js [--app <round-157 copy>] --runs 1 --no-code-cache --trace …`, before and
after interleaved under the shared check lock; this round adds `style` (UpdateLayoutTree / RecalculateStyles) and
`cssParse` (ParseAuthorStyleSheet) to the report's trace numbers. Style recalc before the first screen is ≈ 9 ms either
way: it scales with the elements on screen and the rules that match them, and the moved rules never matched the first
screen. The sheets that moved load with their groups right after the first frame; an `asap` group's sheet arriving
before the `hearth:ready` mark costs one more small recalc, which is the likely +1 ms. Parsing 24 KB less CSS is the
saving (it shows in the parse numbers, which are noisy over two launches).

## How dead was decided (both had to hold)

1. **The tour never matched it.** CDP `CSS.startRuleUsageTracking` through two scripted runs, rule usage unioned:
   `dev/checks/trim-drive.js` (every lazy group loaded, every rail tool opened, palette, "/" menu, a streamed reply,
   1,234 chat commands from a chat, the Lab and the board, ▶ Play) and the new `dev/css159-tour.js` (start, a chat with
   a streamed reply, the "/" menu, a message's right-click menu, every look preset and appearance toggle, Settings with
   every fold open, Trim Hearth, Ctrl/⌘+K, the keys sheet, the command bar, the Alt hints, the usage / downloads /
   backups / find dialogs, every rail tool, the Lab's toolbar menus, `/stage show`, the Lab's Plain look).
   `node dev/smoke.js --fake-engines --coverage <file> --script …`.
2. **No code can produce its selector.** `node dev/css159-dead.js --cov a.json --cov b.json`: for every selector, the
   class / id / data-attribute names it needs (outside `:not` / `:is` / `:where` / `:has`) are looked up in every app
   file that isn't CSS (JS, HTML, JSON; dev/ and docs/ left out). A name counts when it appears anywhere except right
   after a `.` or `#` (that is a querySelector or a style written by JS: it finds a class, it never sets one), and a
   name built from a fixed part keeps its whole family (`ly-${x}`, `'is-' + s`, `` `${k}-row` ``). A rule is dead when
   every selector of its list needs a name nothing produces; a selector list loses only its dead selectors.

The static side turned out to be the strict one: of 3,347 class names in the stylesheets, only a handful are produced by
no code. Most of the CSS for removed UI isn't in the first screen's sheets (round 116 deleted the music studio's files
with their CSS); what is left is mostly in `tools/three-*.css`, which this round doesn't touch (below).

## Moved: eager rules only a lazy group's code can make match (≈ 23 KB out of the first screen)

`node dev/css159-dead.js --movable` lists, for each rule of the first screen's sheets, a name every selector needs that
only files of one lazy group produce (prefix families included: a name some eager file could build stays). Such a rule
can't match before that group has run, so it can load with the group. Two things keep the cascade identical:

- **Same place.** lazy.js' new `cssAfter`: a moved sheet goes in right after the eager sheet it came from (after other
  sheets moved there before it), not at the end. A page without that eager sheet (the Lab window has 12 of the 20, the
  apps window 1) never had those rules: there the sheet isn't loaded at all. Declared in lazy-data.js `CSS_AFTER`
  (merged into the groups' `css` there, so boot-test, trim weights and the manifest see them).
- **No rule left behind can lose or win differently.** Moved, a rule comes after the rest of its old sheet. If a later
  rule of that sheet that stays could style the same element (its subject's classes are all written by that group's
  files, or it has none) with the same specificity and a property in common (a shorthand and its longhands count as
  one), the moved rule stays too — repeated until nothing changes. Rules moving together keep their order.
- Only blocks of ≥ 1.2 KB per sheet → group moved (smaller ones aren't worth a request).

## Zero visual change: how it was checked

`node dev/css159-diff.js shoot <dir> [--app <copy>]` runs the tour with animations, transitions and the caret
stopped, takes 31 window pictures and, with each, a hash of every element's computed style (with its ::before /
::after when present; the run's temp folder taken out of file URLs). `compare` reports differing pixels per view and
differing elements per view. Before = a copy of round 157 (7798cf7) through `--app`.

Result (31 views + the final picture, round 157 copy vs this round):

- **Pixels: no UI pixel changed.** 18 views are identical to the pixel. In the others only these differ: the clock in a
  reply's footer and its tooltip (the time the run happened, 23–55 px), the Trim Hearth panel's KB column (97 px: the
  board and capture features now weigh a few KB more, since their moved CSS is counted with them — text, not style),
  and the Lab's spinning cube (2,178 px along its edges: it is caught at a different angle).
- **Computed styles: identical** on every element in 22 views (start, chats, the "/" menu, the message menu, the three
  looks, Settings in four positions, the palette, the command bar, the Alt hints, the dialogs, Forgeheart). Where some
  differ, it follows the content, not CSS: Trim's rows (their KB text, 10 elements), 8 lines deep in the keys sheet,
  6 progress fills in the Projects home and Settings views, 4 in the Lab. The Lab's own DOM, kept while another tool is
  in front, differs in 829–865 elements in those views; a direct probe of the same elements in both builds (the Lab's
  toolbar, its groups and its header: shown, hidden behind the board, and after going back to a chat; 3 × 4 elements,
  6,236 property values) found **0** differences, and the Lab view itself differs only in 4 progress fills, so this is
  the Lab's state at that moment of the tour (it isn't the same from run to run), not the moved rules.
- The first attempts showed every element differing: the hash had read file URLs with the run's temp folder in them and
  listed custom properties in declaration order (which follows the sheets they are declared in); both are now
  normalized in `dev/css159-tour.js`.

## Seen, not changed

- **look.css (59 KB) is the biggest first-screen sheet**, and most of it is per-look rules (`:root[data-look~=…]`):
  only the active look's apply. Loading the inactive looks' rules lazily would need Look's apply-before-first-frame to
  wait for the sheet (as Swirl's does): a design change, not dead CSS.
- 48 KB of the first screen's 374 KB are comments (polish.css alone 19 KB). boot-test counts CSS with its comments
  (JS without); they were left alone (notes for people).
- In the drive, 41 KB of features.css and 41 KB of polish.css never matched, but their names are produced by live code
  (the Lab's older panels, tooltips, states) — by this round's rule they stay. The Lab-only part that could move is
  limited by name families (`lab-`, `stage-`, `tw-` prefixes are also built by eager files and studio.js).
