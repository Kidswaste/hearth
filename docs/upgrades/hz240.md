# hz240 (round 17): the whole UI at 240 Hz

You asked for "a smooth 240 Hz at all times": 4.2 ms per frame. This pass is the interaction feel everywhere outside the
Lab picture: the rail, the chats list, chats, menus, the Ctrl/⌘+K palette, the Commands page, the board and Lab
chrome, settings, dialogs, toasts. Nothing was removed; a few effects now run on the compositor instead of the main
thread (they look the same, or within a hair).

## How it was measured
`dev/checks/hz240.js` (new, in the `smooth` group) drives the app with **real input events** (CDP mouse, wheel and key
events, the way a person would), in the Forgeheart look, under a timeline trace, over 13 stretches: idle, hovering down
the rail and the chats list, wheeling the chats list and a 300-message chat, the chat ⋯ menu ×5, right-click on chat
rows ×5, the palette ×4 (open, type, arrows, Esc), typing 60 letters, dragging the Appearance glow slider, switching
tools from the rail, the Commands page (hover down the list, wheel through it, search), toasts. `dev/trace-stats.js`
turns the trace into, per stretch: input → next commit latency and the main-thread work in it, drawn frames whose work
went over 4.2 ms (240 Hz) / 8.3 ms (120 Hz), long tasks, **forced layouts with the JS line that asked** (style or
layout read inside a handler, a timer or a frame callback), style recalcs (count, elements) and layouts (count,
objects), and where the main-thread time went (style, layout, paint, layerize, commit, scripts).

Numbers below: two interleaved runs each of the round-16 build and this one, same machine (Xvfb + software GL, shared
CPUs, so the absolute frame times are several times a real Mac's and the vsync here is 60 Hz). The counts (forced
layouts, elements restyled, objects laid out, long tasks) are the reliable ones; per-frame work also carries this
machine's software compositing.

## Upgrades

### Measuring (for the next rounds too)
1. `dev/checks/hz240.js`: the 240 Hz interaction check (real input, 13 stretches, the owner's look); `window.HZ_ONLY`
   runs some stretches, `window.HZ_CSS` tries a CSS change for an A/B, `window.HZ_RAW` prints every number. In the
   `smooth` group of `sh dev/run-checks.sh`.
2. `dev/trace-stats.js` + `smoke({ trace: 'stop', detail: true })`: long tasks, frames over 4.2 / 8.3 ms, forced
   layouts with the JS file:line that asked, input → commit per marked stretch (`performance.mark('hz240:<name>')`),
   where the main-thread time went and the busiest scripts. `{ dump: path }` saves the raw trace.

### Pointing and hovering
3. Forged tooltips measure nothing while the pointer moves: the "is this text cut short?" test and the placement run
   once, when the tip is due, in an animation frame (with the frame's own layout).
4. One tooltip node, made once and reused (it was created and thrown away for every tip).
5. The tip no longer asks for `:hover` before showing (a fresh style pass each time): it knows what you point at.
6. The chrome sheen crossing a button you point at (rail buttons, ghost buttons, chips, look tiles, Shuffle, Lab tabs,
   node headers, `m-chrome` / `m-gold` / `m-sheen`) is a streak the compositor moves; it was a background-position
   animation that repainted the button for 0.6 s, a dozen at once when you crossed the rail.
7. Forgeheart rail buttons ease only their nudge (no filter / box-shadow transitions repainting per frame).
8. Swirl look: a chat row's hover nudge moves its text with a transform (it changed padding: a layout of the whole
   chats list per hover).

### Pressing
9. Press glints, the Send ring, Tap / Freeze rings and Save embers measure the button in the next frame instead of in
   the pointerdown (a forced layout at the start of every click).
10. The sparks' colors (gold, ember, cyan…) are read once per look instead of on every press and toast.
11. The rail button's own color is read from the button, not from a computed style.
12. The 🎲 Shuffle roll, the Lab slider flash, the keys-sheet flash and the ↻ Again flash replay without forcing a
    reflow.
13. Tap (your most-used Lab button): its flash is a gold layer whose opacity plays on the compositor, restarted on every
    tap with no reflow (it was an animated inset shadow plus a forced reflow per tap).

### Menus and the palette
14. Menus stay in the top layer between openings (hidden), so opening one no longer runs a whole-page style pass for
    `showPopover()`; they're shown afresh only when something else went on top or a dialog is open.
15. Only the first rows of a long menu slide in (each sliding row was a compositor layer).
16. The Ctrl/⌘+K palette is built once and reused: rows are kept and only their changed text is written, one listener
    for clicks and one for pointing (two per row before, rebuilt on every keystroke).
17. The palette opens in two steps: the card and the last list at once, the fresh ranked list in the next task (what
    you've typed by then is kept).
18. Palette items are gathered once per opening (twice before) and lower-cased once (not on every keystroke).
19. ↑ / ↓ in the palette scroll the list in the next frame (no reflow per key).

### The Commands page (≈ 990 commands)
20. The list is drawn in pieces: what fills the screen at once, the rest 3 ms at a time between frames (the whole list
    in one go held the page for 100+ ms on every search).
21. Rows are kept and reused between redraws (search, pins, runs moving).
22. Each section (heading + rows) is skipped by the browser while off screen, so only the headings near the screen are
    sticky (thirty sticky headings were thirty layers to rebuild on every scrolled frame).
23. Still posters carry no animation (paused animations made each one a layer: layer building while scrolling the page
    1,656 → 204 ms); a preview starts from its first frame when you point at it.
24. Posters are drawn a section at a time as it nears the screen (one watcher per section instead of one per row: the
    per-frame visibility work while scrolling fell by ~85 %), a few per frame.
25. A preview starts once the pointer rests on a row (70 ms), not on every row the pointer crosses.
26. Redrawing while you're far down the list draws enough rows to keep your place (no jump to the top).
27. Searching resets the scroll before drawing (it forced a layout of the new list just to scroll it).

### Chats, the rail, the panel, the window
28. Chats you aren't looking at, the Board and the Commands page skip style, layout and paint while hidden (their
    content, scroll and sizes are kept): a page-wide change (the look, the glow, a resize) no longer restyles them.
    The Lab, websites and other tools keep running hidden as before.
29. Dragging the chats panel's edge changes only the panel, once a frame; the page-wide width is written when you let
    go (it restyled every element per pointer event).
30. The Forgeheart game / chat divider follows the pointer once a frame.
31. Toasts clear a docked chat's composer without a page-wide `:has()` rule (every hidden flip anywhere made the
    browser search the whole page again).
32. A dead `:root:has(.msg.streaming…)` rule is gone (checked again on every node a streaming reply added).
33. The board's Alt+wheel (opacity / rotate the selection) listens on the board only: a page-wide wheel listener that
    could cancel made **every scroll in the app** (chats, lists, menus) wait for the main thread before moving.
34. The board's "am I visible?" test, run on every click in the app, checks the cheap things first (it forced a style
    pass per click).

### Settings and dialogs
35. Dragging the Glow slider shows the glow live once per frame and saves when you let go (it saved the config on every
    step, which re-applied the whole look and redrew the chats 30× per drag).
36. Dialogs come in with opacity and a slide only (the 2 px blur was a full-dialog filter per frame); same for the Swirl
    look's entrances.
37. Forgeheart's scan-in for dialogs, the palette and menus is opacity + a short unfold (it animated clip-path).

### Loops that ran while something was going on (now on the compositor)
38. The Stop button's breathing light while a reply is written: a still inner glow whose opacity breathes (it animated
    a box-shadow for as long as the reply lasted).
39. Forgeheart Classic's Stop pulse (cut off by the corner clip, so invisible) no longer repaints every frame.
40. The unread diamond on the rail breathes with scale / opacity (its box-shadow ring repainted every frame).
41. A chat at work (its header glyph, the scene avatars over the Lab picture) glows with opacity / scale instead of
    box-shadow + filter.
42. The flowing edge of running cards (Claude ⇄ Astra collab, compositing, intro video, jam) slides on the compositor
    (background-position before).
43. The meter strip's live line flows with a transform (a turning conic gradient repainted the strip every frame).
44. The meter's live letter blinks in two steps (2 repaints a second instead of 60+).
45. Recording, Write armed and Live sound in the Lab's media bar breathe with opacity over a still ring (they animated
    box-shadow next to the playing picture).
46. The intro video's live beat frame breathes the same way.
47. A board clip still loading breathes (its shimmer moved background-position).
48. 18 transitions no longer animate box-shadow or filter (inputs, buttons, ghost buttons, rail, node wires, jam
    frames, Swirl buttons): those change at once; transform, opacity and colors still ease.

### Work behind the scenes, off the interaction
49. The usage decorate pass ignores tooltips, sparks, menus, the palette and the Commands list coming and going (a
    tooltip or a click re-ran it over every toolbar 0.8 s later).
50. Command links in replies are looked for only when replies or notes change (any tooltip or menu re-scanned the
    page 250 ms later).
51. The weekly tidy's look at a new screen waits for an idle moment (it could land mid-interaction 2.5 s after you
    opened something).

### Lab
52. The Lab's **Max fps follows your screen**: the adaptive resolution aims at the frame interval your display actually
    gives (60 / 75 / 90 / 120 / 144 / 165 / 240 / 360 Hz, learned from the shortest frames), so on a 240 Hz screen a
    scene running at 60 counts as slow and lowers its internal resolution to catch up (it always aimed at 60 Hz).
    `__labHealth().hz` shows the rate it found.

Electron, checked (no change needed, not counted): the main window has no frame cap and no vsync / frame-rate-limit
switches, so Chromium follows the display (120 Hz ProMotion on the Mac, 240 Hz on Windows); hidden windows still rest
(background throttling on, as it should be); the Lab stage window keeps running hidden on purpose.

## Still costly (next steps, not done here)
- Wheeling through a long chat: the frames that draw never-seen messages are dominated by painting / rasterizing new
  content (unchanged here).
- The chat's scroll handler reads the scroll height each scroll event (inside the frame, so not double work).
- The glow slider still restyles the whole page once per frame while dragging (it's a page-wide color): fine at 120 Hz,
  tight at 240 Hz on a big window.
- The node editor's flowing wires animate `stroke-dashoffset` (main thread) and Swirl's tab underline moves its mask.
- Opening a menu or the palette reads its size once (its own style + layout): needed to place it.
