# cw103: a giant windowed chat's window tasks well under 60 ms of their own CPU (round 103)

At round 102's release the `chatwindow86` app check (opt-in, `CHATWINDOW86=1`) failed 1 of 2 runs. Since checks102 it
judges each long window task by the window thread's **own CPU** in it (`dev/trace-stats.js longTasks`). The failing
tasks were 62–79 ms of real CPU against a 60 ms budget, in four steps of bigchat84's giant chat (6,000 messages,
63 MB, opened windowed):
- **open**;
- **top** (scroll to message #1);
- **edit** (edit-from-here on an older message of yours);
- **sync** (a changed version of the chat arrives: let go, opened again).

This round profiled each of these steps on HEAD (729f245), split every task over ≈ 30 ms into its pieces, and took
the causes out one by one. In 6 runs of the final code (5 on the shared box, 1 under a CPU burn) the costliest window
task of these four steps was **42 ms** of its own CPU (open), and 37 / 23 / 19 ms for edit / top / sync. On HEAD the
same steps reached 58 / 73 / 54 / 82 ms, and all three HEAD runs failed (sync, edit, edit and sync; the first also
find). Every final run passes. Nothing about what the chat shows or saves changed (below: "Behaviour").

## How it was measured
- **The trace per step.** `dev/checks/chatwindow86.js` already traces each step (`dev/smoke.js { trace: 'start',
  tasks }`) and judges the window's long tasks against the budget (`trace-stats.js longTasks`, `mark: cw86:<step>`).
  With `window.CW86_TRACECATS` set to the timeline categories (plus `disabled-by-default-v8.cpu_profiler` for the JS
  samples) and `window.CW86_DUMP`, each step's trace was saved and split: every top-level task on the window thread
  with its own CPU (`tdur`), its children (script by file:line, style recalcs with their element counts, layouts with
  their objects and the JS line that forced them, GC), and the JS samples inside it.
- **Before**: HEAD (729f245) as an archive in a temp folder, run with `dev/smoke.js --app <it>` and today's check.
  **After**: this branch. The same fixture (`/tmp/hearth-bigchat84`), the same lock (`flock /tmp/hearth-run.lock`).
- **Load-aware**: each cell gives the step's costliest window task as **its own CPU / its wall time**, then the
  step's wall time, then the check's verdict for that step (✓ under budget; ≈ "can't tell": over the budget on wall
  time only, the rest being the thread's wait for a CPU; ✖ over on its own CPU). Tasks that are only a garbage
  collection are left out of "costliest" and listed apart (the check's observer doesn't report them; see "What's
  left").
- **The box**: 4 CPUs, SwiftShader under Xvfb, shared with the syncstall103 stream's Node runs (load 2–5). The same
  work costs up to ≈ 1.6× more CPU from one minute to the next here (checks102 found the same), so every number is
  from several runs.
- **The CPU burn** as checks102 ran it: `burn.js 6 mix` (worker threads, half spinning and allocating, half reading
  and writing at random over 64 MB each), in its own session at nice −8 (this box schedules by session; the app runs
  at −8), bounded by `timeout`.

## What each task was made of (HEAD), and what changed
### open (and the redraws that draw a giant chat's end)
- **The draw's own task (render, ≈ 25–45 ms).** `planOf` walks the 300 resting blocks. For each one it read the date
  of the block's last message: `chat.messages[hi - 1]?.at`, which makes a stub (a Proxy and a JSON parse of its
  record) and formats a date with Intl, 300 times. `paintContext` and `longChatBanner` looked for the last usage with
  `[...chat.messages].reverse().find(…)`: a copy of all 6,000 entries, so 5,700 stubs made each time.
  - Now a resting run's date is read only when a drawn message follows it (one stub, one date).
  - `dayLabel` is kept per calendar day (the same text: it depends only on the day and today).
  - The last usage is found with `findLast` (from the end, no copy; the same answer, holes included).
- **The first frame (≈ 40–58 ms: layout 332 objects, style 205 elements, the fold measures).** The end was drawn
  with its last 8 messages, which in this chat hold 59,000 characters (one reply alone is 45,000 characters, 584
  lines). Their first layout was the frame.
  - A windowed chat now draws its last **2–4 messages, up to ≈ 16,000 characters**, first. The rest (the earlier part
    of the window, the resting spacers) goes in under it a piece a frame (`drawLater`). A piece is ≈ 300 elements,
    100 characters of a message's text counting as one element. The messages among the list's last 8 children are
    laid out whole (chatcore.css), so they count by size; the ones above are skipped by content-visibility and count
    3 each, so they go in together.
  - Each piece's replies that are in view are folded in that piece's own frame, before it's painted, and the chat is
    kept at its end, as the first frame does. Nothing shows unfolded.
- **The fold measures.** `foldFresh` measured the last 6 replies' heights in the frame. A reply out of view whose
  contents content-visibility skips was laid out just for that: one forced layout each, 3–6 in a frame. In a windowed
  chat such a reply is now handed to the fold watch (`foldWhenNear`, as older replies already were). It is folded
  when it comes near, before you can see it.

### top (scroll to message #1)
- **One task of 54 ms CPU (94 ms wall)**: the woken block's first style (997 elements) and layout (1,384 objects),
  forced by the scroll correction right after the block took its spacer's place (`chat-rest.js wake`).
- Now a woken block goes in **a piece a frame** (≈ 260 elements, text counted as above):
  - from its end up when the view is under the block: each piece right under the spacer;
  - from its top down when the view is above the block or in its upper half: each piece right over the spacer. At the
    very top, #1 shows with the first piece: the climb to the top takes what it took before (≈ 0.93 s).
  - The spacer gives up the height each piece took, so nothing on the far side moves. What's at the top of the view
    is kept after each piece, and the last piece takes the spacer's place exactly as the whole block did (the same
    proportion of the block in view when the view was inside the spacer).
- A jump or a find waiting on a block (`hurry`) takes pieces twice as big, one task each without waiting for a frame,
  and the piece holding its message goes in last. The message then appears when the jump lands on it (it showed
  before the scroll at first: a run under the burn found it off screen). The step takes 0.70–0.88 s against
  0.62–0.66 s on HEAD: the pieces' tasks add ≈ 0.1–0.2 s before the jump lands.

### edit (edit-from-here on an older message)
- **The reply's end (≈ 50–75 ms).** The fake engine answers within ≈ 0.3 s, while the new end was still being drawn.
  - The "done" event's redraw read `nearBottom` and then `scrollTop`. That laid out everything painted since the
    last frame inside the event (reply text and the end part: 493 elements, 626 objects).
  - It then placed the whole window part at once: one frame of ≈ 600 elements and 750 objects.
- **The send's own task** walked all 6,000 messages by role, several times:
  - chat-cost's send hook (`filter` over every message, for "is this the first exchange?");
  - offline's continue-line check (`findLastIndex` over every message, then only the last 3 used);
  - the finish hooks of access, hooks and routines (`[...chat.messages].reverse().find(…)`).

  Each read every older message's record the first time: 25–45 ms.
- Now:
  - **A scroll to the end already due this frame** (`scrollToEnd`'s `endRaf`, set only while the reply is followed)
    counts as "at the end". It isn't measured; the redraw then follows to the end, which is what that frame was going
    to do. The old scroll offset is read only when the place may be kept.
  - **A redraw of a giant chat followed at its end** (the ↓ button hidden) **while its earlier part is still going in**
    draws its end first again, and the rest in pieces. The same applies when the redraw has its messages to make.
  - chat-cost counts talk messages until it has 2 (`some`, which skips holes as `filter` did). offline reads only the
    last 3 messages, all it ever used. access / hooks / routines use `findLast`. The answers are the same.
  - **The records are read ahead, in idle moments** (`chatwin.js warm`). Right after a windowed chat opens, or goes
    back to its window, its older messages' records are parsed ≤ 4 ms at a time (`'role' in stub`: parsed, never a
    miss). Any walk by role later finds them read. This is the same work as before, done earlier and in slices.
    Nothing is fetched or loaded.

### sync (a changed version arrives)
- **One frame of 82 ms CPU (156 wall).** Sync's `Native.refresh(…, { keepScroll: true })` rebuilds every node
  (another chat object). The whole window part (538 elements, 384 objects) went in in one frame, and the fold measured
  6 replies with a forced layout each (27 ms of it).
- Now that redraw is "followed at its end, with its messages to make": its end first, the rest in pieces, the folds
  as above. Its costliest task is now 17–19 ms.

### Also changed (they failed runs on the way)
- **/export of a long chat** writes ≈ 0.5 MB parts instead of 2 MB. Encoding and sending one 2 MB part was one window
  task of 75–130 ms on a busy box, and it failed a run on HEAD under the burn. `chatexport-core.js pump`'s `part`
  option: the file is the same, byte for byte (the check compares it).

## Behaviour
- What the chat shows and saves is the same:
  - the same messages in the same order, the same folds, the same place in view;
  - the same saves by change, the same export file, byte for byte.
- `unit:chatwin-scan` passes: 98 files audited. native.js reads `.messages` on one more line: the drawn end's text
  length, from its loaded messages only.
- The rules from chatwindow86 hold:
  - "not loaded" is never "not there": the read-ahead uses `in`, which parses a record and never misses;
  - a store read failure is never "empty";
  - deletes go to the Trash; nothing is uploaded; no real data was used.
- **What you could see differently** (on a slow computer, for a frame or two):
  - a giant chat's end shows first and the messages just above it come in the next frames. Before, the last 8 came
    together. They're above the view at the end;
  - a block woken as you climb fills from the side you're looking at, a piece a frame, instead of in one stall;
  - a long chat's reply out of view folds as it comes near, not in the frame it was drawn.
- The changes to drawing order and folding apply to windowed chats only (≥ 8 MB on disk). Two changes apply to every
  chat:
  - the block-by-piece wake (chatwindow72's resting blocks); `chatwindow72` passes;
  - render's "a scroll to the end already due counts as at the end". It only differs when a reply ends before the
    frame after its first paint. Before, the redraw then measured the list with the new text not yet scrolled to and
    kept the old place: the reply ended below the view while the chat still said it was following. Now it follows to
    the end, as it does when that frame came first.
- First screen: 1689 / 1696 KB (was 1687). native.js grew by ≈ 2 KB; chat-rest.js and chatwin.js are lazy.

## What's left
- **Major garbage collections of 55–75 ms CPU** happen once per run, after the check's load-whole steps (panels,
  export) let go of the 60 MB they held. They show in the step after: react, or edit on HEAD too. Each is a task that
  is only a GC (`V8.GC_HEAP_EPILOGUE_SAFEPOINT` 30–40 ms, embedder tracing 12–20 ms). The window's long-task observer
  doesn't report it, so the check doesn't judge it. It isn't chat drawing; the 60 MB come from loading the chat whole,
  which only export and similar actions do.
- An idle-time task right after an idle callback (recall's index slice, 0.3 ms) once took 72 ms of CPU with no traced
  work (one run, sync step). It looks like V8's idle-time collection. The check judged it "can't tell" on the wrong CPU
  figure, 0.3 ms: `longTasks`' overlap match took the idle callback's events. That is worth a look in trace-stats.
- **panels** (budget 100: chatsafe's reader and its "Show earlier") has a 44–74 ms layout task. It's unchanged and
  not one of the four.
- export's whole-chat load (15 ranges of 400, then the file in 0.5 MB parts) still has tasks of up to ≈ 50 ms.

## For the patch notes
- **Very long chats are smoother.** Opening a chat with thousands of messages, scrolling to its very top, editing an
  older message and getting a new version from your other computer no longer make Hearth stall for a moment. The
  longest pause in each went from about 0.06–0.08 s of work to under 0.045 s. The messages just above the end, or the
  older ones you scroll up to, now come in over a few frames instead of all at once.
- Exporting a very long chat writes it in smaller pieces, so the app stays responsive while it saves.
